# PostgreSQL Migration Guidelines

This skill defines the mandatory rules and best practices for creating and modifying PostgreSQL database schemas within this project.

## How It Works

When a user requests to create a new SQL file or modify the database schema:
1. Verify that the request strictly adheres to the "Append-only" migration rule.
2. Ensure any new tables include the mandatory standard audit columns.
3. Validate that data types and practices align with the project's PostgreSQL standards.

## Mandatory Rules

### 1. Append-Only Migrations (Strictly Enforced)

The database schema is managed via sequential migrations.
- 🚫 **NEVER MODIFY OLD SQL FILES:** Once an SQL file is created and run, do not edit it to add or change columns. Modifying historical migration files will break the database state.
- ✅ **ALWAYS CREATE A NEW SQL FILE:** Any changes (adding columns, renaming, dropping, altering data types, adding indexes) MUST be written as `ALTER TABLE` statements in a completely new SQL file.

**File Naming Convention:**
Migration files must indicate execution order (e.g., sequential numbers or timestamps) and their purpose.
*Examples:*
- `001-create-users-table.sql`
- `002-create-groups-table.sql`
- `003-add-avatar-column-to-users.sql`

### 2. Standard Audit Columns

Every main table created in the system MUST include the following standard columns for tracking and soft-delete mechanisms:

```sql
    id          varchar(26) PRIMARY KEY NOT NULL, -- Mandatory: ULID format
    params      jsonb,
    created_at  timestamp with time zone NOT NULL,
    created_by  varchar(255)             NOT NULL,
    updated_at  timestamp with time zone,
    updated_by  varchar(255),
    deleted_at  timestamp with time zone,
    deleted_by  varchar(255)             null
```

**Column Details:**
- `id`: The primary key. It MUST use the **ULID** format (`varchar(26)` or `char(26)`). ULIDs are 26 characters long, time-sortable, and offer significantly better indexing and sorting performance compared to standard UUIDs.
- `params`: A flexible `JSONB` column to store extended configurations or secondary metadata without the need to constantly alter the table structure.
- `created_*`: Records the creation timestamp and the identifier of the creator (Mandatory).
- `updated_*`: Records the timestamp and identifier of the user who last updated the record.
- `deleted_*`: Supports the **Soft Delete** mechanism. When data is "deleted", update `deleted_at` with the current timestamp instead of running a physical `DELETE` command.

### 3. PostgreSQL Best Practices

- **ULID Generation:** ULIDs should ideally be generated by the backend code (Node.js/Bun) before insertion, allowing the application to know the ID immediately without waiting for `RETURNING id`.
- **Time Zones:** Always use `timestamp with time zone` to prevent time shifting errors across different server locations.
- **Text Fields:** Use `varchar(255)` for fields with a known length limit, and `text` for unbounded content.
- **Indexing:** Proactively write `CREATE INDEX` statements for frequently queried columns (e.g., indexing `deleted_at` to quickly filter out soft-deleted records).
